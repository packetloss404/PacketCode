# `packetcode run` versus ACP — 2026-09-01

## Question

Does ACP add enough client/protocol or permission latency to explain the
earlier observation that PacketCode was slower at coding work?

## Method

- Windows/amd64, working tree based on `d646094` with the uncommitted shared
  runtime and headless-run changes under test.
- Prebuilt PacketCode executable; compilation was outside both measurements.
- OpenAI `gpt-5.6-sol`, `read-only`, fresh session for every sample, no MCP
  servers, and an isolated temporary `PACKETCODE_HOME`.
- Three pairs with order alternated: run/ACP, ACP/run, run/ACP.
- Wall time began before process start and ended when the completed response
  was available. ACP initialize, session creation, and prompt round trip were
  also recorded.
- The prompt required exactly one `read_file` of lines 1–12 of `go.mod`, then
  an exact two-line answer. Every measured sample produced the same output
  hash and byte count, two provider calls, one tool call, 10,318 input tokens,
  51 output tokens, and zero approvals.

The raw report is
[`data/run-vs-acp-2026-09-01.json`](data/run-vs-acp-2026-09-01.json). It stores
hashes and sizes, not model response text or credentials.

## Result

| Metric | `run` | ACP |
| --- | ---: | ---: |
| Wall time, median | 4.152 s | 4.027 s |
| Wall-time range | 4.126–6.050 s | 3.482–4.382 s |
| Internally reported/prompt time, median | 4.077 s | 3.881 s |
| ACP initialize, median | — | 61 ms |
| ACP session creation, median | — | 18 ms |
| Provider calls per sample | 2 | 2 |
| Tool calls per sample | 1 | 1 |
| Approval requests | 0 | 0 |

The paired ACP-minus-run deltas were +0.230 s, -0.644 s, and -2.023 s;
the median was -0.644 s. The median end-to-end difference between paths was
only 0.125 s (about 3%), with ACP slightly faster. That direction is not a
claim that ACP improves engine speed: both paths share the same runtime and the
sample-to-sample live-provider spread was much larger than the path median.

One cache warm-up detail differed. The first `run` sample reported 9,976 cached
input tokens while the paired ACP sample and every later sample reported
10,312. Total input/output and executed work still matched. The first pair is
therefore useful end-to-end evidence but not a perfectly cache-matched pair.

## Rejected pilot

The first three-pair prompt asked the model to inspect four files. It was
policy-identical and had zero approvals, but the model chose 3–7 provider calls
and 5–6 tool calls, leaving zero work-matched pairs. Its apparent path medians
were discarded. This is why the recorded benchmark pins tool count and output,
not just prompt text and permission mode.

## Decision

The suspected ACP permission round trip was not present: the controlled task
needed no approval on either path. ACP process initialization plus session
creation was about 79 ms at the median, not enough to explain coding-task
latency, and the end-to-end result shows no ACP penalty worth optimizing.

Do not add public phase-timing fields or change the engine for this result.
Provider latency dominates the remaining variance, while local tool and
protocol work are bounded and identical here. Revisit opt-in, versioned phase
observability only if a larger controlled workload shows a repeatable residual
after matching provider calls, tool calls, approvals, output, and cache state.
